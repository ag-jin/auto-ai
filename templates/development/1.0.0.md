# 开发交付

适用于功能实现与缺陷修复。模板规定方法，项目自己的规则决定具体实现与检查要求。

## 主会话安排

1. 将 Issue 归一化为 `goal`、`acceptance`、`scope`、`context`，核对缺口与已有授权。
2. 固定模板引用、要求版本和本次执行标识，将完整执行包交给一个 Worker。
3. 同一项目默认只安排一个写入者；需要并行时，明确任务相互独立并隔离工作目录。

## Worker 执行

1. 读取项目规则与相关代码，确认现状。修复任务先建立可复现的证据；无法复现时记录原因。
2. 形成足够指导当前工作的短计划，按范围实施；影响目标或验收的缺口交回主会话处理。
3. 运行与实际改动相符的检查，记录命令、退出结果和对应代码版本。失败时分析原因并在本次预算内修复。
4. 返回改动摘要、产物引用、实际验证证据和未解问题。

## 主会话核验与交付

- 核对结果对应当前要求版本，检查证据实际对应的改动版本。
- 按项目规定与改动风险安排独立评审；独立评审必须使用新的 Worker 上下文。
- 检查失败交回修复，缺少关键决定则进入等待；不把 Worker 的“已完成”直接等同于任务完成。
- 达到验收要求后更新 Issue，关联产物或 PR。PR 的合并与发布按项目已有授权处理。

## 统一返回格式

| 字段 | 内容 |
| --- | --- |
| `summary` | 做了什么，结果是否满足目标 |
| `artifacts` | 文件、commit 或 PR 引用 |
| `evidence` | 检查对象、命令/方法、结果和日志入口；区分 passed / failed / not_run |
| `blockers` | 仍需哪个具体输入、决定或外部条件；没有则为空 |

返回结果同时带 `run_id`、`attempt`、`requirements_rev` 和 `template_ref`，由主会话识别重复或过时结果。
