# 版本化双路 SOP 开发

适用于一次需要两路并行实现的已批准开发任务：批准稿在整个 Run 内固定不变，两条 lane 在各自独立的 Pi 会话与 worktree 中并行实现，按 checks 定向验证与返工，汇总后由独立 reviewer 复核，最终仍走现有真实 PR 流程交付一个 PR，不自动合并，也不是用户最终验收。

## 固定引用

- 本 Markdown 与同 commit 的 `templates/development-sop/1.0.0.yaml` 一起固定，YAML 是唯一流程定义：`sop: development-sop@1.0.0`、`handoff: development-result@1.0.0`、`review: review-result@1.0.0`、`max_reworks: 1`。
- 批准稿的 `context` 就是用户批准的 YAML，只使用 `sop`、`lanes`、`checks` 三个键，其中 `sop` 可省略，写了就必须是 `development-sop@1.0.0`：
  - `lanes` 恰为两路：`{id: develop-a, path: <仓库内相对文件>, goal: ...}` 与 `{id: develop-b, path: ..., goal: ...}`；两个 `path` 不相同，且都在批准稿的 `writeScopes` 内。
  - `checks` 非空，每项为 `{lane: develop-a|develop-b, args: [...]}`，只引用这两条 lane。
- `acceptance` 是自然语言验收，原样、逐项交给 reviewer，不得改写或合并。

## Lane 交付

- 每个 lane 的 Pi 最终输出纯 YAML 映射：`{sop, template: development-result@1.0.0, draft_rev, step, artifact}`，不包裹其他文字；`step` 是该 lane 的 id，`artifact` 必须等于该 lane 在批准稿里的 `path`。
- 两路都通过交接校验后，才把各 lane 的唯一交付文件汇总到父工作树；任一路未校验通过时父树不写入。
- 证据写入证据目录，不提交进代码。
- checks 的 `args` 只作为 node argv 直接执行：第一个元素必须是固定基线中仓库内的 `.mjs`/`.cjs`/`.js` 脚本路径，不经 shell；其余参数原样传给已批准的脚本。

## 检查、返工与复核

- 任一 check 失败时，把失败证据退回该 check 的 `lane`，另一路不重跑。
- 汇总后由独立 reviewer 优先以 `draft` 角色（无工具）复核批准稿、最终 diff 与测试，最终输出只含 `sop`、`template: review-result@1.0.0`、`draft_rev`、`outcome: approved|changes_requested`、`reason`，以及下述按结论要求的 `acceptance` 或 `step` 的 YAML；`step` 为 reviewer 标出的有效 lane id。
- `outcome: approved` 还必须带 `acceptance` 字符串数组：条数与顺序严格对应批准稿的每个验收项，每项非空，并逐项引用最终 diff 或检查证据说明该项如何满足；缺少、条数不符或空项都不得交付。
- `changes_requested` 不要求 `acceptance`，只退回 reviewer 标出的有效 lane，且整个 SOP 仅允许一次返工（`max_reworks: 1`）。
- 汇总后的测试跑稿、独立代码验收与真实 PR 沿用现有流程：仍是一个 Task Run、一个 PR；PR 正文固定使用本 Run 的模板 pin，并逐项列出批准稿验收项与对应评审证据。
