# 开发交付

适用于功能实现与缺陷修复，支持多仓库和独立任务并行。项目规则决定具体实现与检查要求。

## 主会话安排

1. Issue 筛选只形成候选。先整理目标、范围、验收与待决策项，获得用户对当前任务稿版本的明确开发决定。
2. 按固定 commit 下的 [Worker 任务稿格式](../../docs/WORKER_BRIEF.md) 生成完整执行稿，保留目标、事实来源、允许范围、接口、验收与回报约定。
3. 固定仓库、Issue、任务稿版本、模板 commit/version、模型配置和执行标识。每个开发 Worker 使用独立会话、worktree 与任务分支。
4. 核对已有执行，按全局/仓库上限、优先级、显式依赖和写入范围冲突派发。阻塞任务排队，不妨碍其他就绪任务。跨仓库依赖也必须记录。

## Worker 执行

1. 读取项目规则与相关代码，核对当前状态。修复任务先复现；已有修复或事实变化需说明并保留。
2. 按范围实现并运行实际检查，返回可检查产物。接口不明确时说明缺少什么，不扩大授权。
3. 证据覆盖正常路径与关键失败边界，聚焦产品行为；模型、凭据和控制进程由监督者核验，不探测个人配置或密钥。
4. 返回改动、实际命令/结果、未验证内容与具体阻塞。

## 主会话核验与交付

- 独立复跑关键验收，核对当前任务稿、代码和证据版本。缺陷反馈包含最小复现、实际/期望行为、修改范围及回归要求。
- 可验收的小步及时提交、集成与推送，产物和 PR 明确关联仓库、Issue 与执行标识。
- 未经最终验收不合并 PR；用户和设计监督的结论对应当前 PR head，合并由用户明确发起。
- 保存代码和必要证据后及时归档 Worker worktree。活动、未提交或结果未知的现场保留并说明原因；日志集中保存。
- 需求版本改变后旧授权失效。模板升级不改写在途执行的固定引用。

## 返回格式

`summary`：结果；`artifacts`：文件/commit/PR；`evidence`：对象、命令/方法、结果与日志入口；`blockers`：具体缺口或空数组。另带 run_id、attempt、requirements_rev、template_ref，区分 passed、failed、not_run。

## 升级依据

结合 T001 的真实执行/返修与用户新确认的多仓库并行、用户决定、及时 Git 提交和 worktree 回收要求。保留 1.0.0/1.1.0；在途 T003A 继续使用开工时的 1.1.0。
