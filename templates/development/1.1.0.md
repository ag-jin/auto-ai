# 开发交付

适用于功能实现与缺陷修复。模板规定方法，项目自己的规则决定具体实现与检查要求。

## 主会话安排

1. 将 Issue 归一化为 `goal`、`acceptance`、`scope`、`context`，核对缺口与已有授权。
2. 按 [Worker 任务稿格式](../../docs/WORKER_BRIEF.md) 写出一个可独立验收的工作单元，明确接口、范围与正常/失败样例；参考文件同样读取模板固定 commit 下的版本。
3. 固定模板引用、要求版本、实际模型配置和本次执行标识，将完整执行包交给 Worker。
4. 派发前核对已有执行记录与进程；同一任务已有执行时先恢复监督。同一项目默认只安排一个写入者。

## Worker 执行

1. 读取项目规则与相关代码，确认当前状态。修复任务建立可复现证据；当前状态与任务稿不一致时先说明差异。
2. 形成足够指导当前工作的短计划，按范围实施；影响目标或验收的缺口交回主会话处理。
3. 运行与实际改动相符的检查，覆盖接口的正常路径和关键边界。失败时分析原因并在本次预算内修复；证据针对产品行为。
4. 返回改动摘要、产物引用、实际验证证据、未解问题及未验证内容。

## 主会话核验与交付

- 核对结果对应当前要求版本，检查证据实际对应的改动版本，独立复跑关键验收。
- 按项目规定与改动风险安排独立评审；独立评审使用新的上下文。
- 发现缺陷时给出最小复现、实际行为、期望行为和修复范围，要求增加回归并复跑；已有修复应被识别和保留。
- 检查失败交回修复，缺少关键决定则进入等待；不把 Worker 的“已完成”直接等同于任务完成。
- 达到验收要求后更新 Issue，关联产物或 PR。PR 合并与发布按项目已有授权处理。

## 统一返回格式

| 字段 | 内容 |
| --- | --- |
| `summary` | 做了什么，结果是否满足目标 |
| `artifacts` | 文件、commit 或 PR 引用 |
| `evidence` | 检查对象、命令/方法、结果和日志入口；区分 passed / failed / not_run |
| `blockers` | 仍需哪个具体输入、决定或外部条件；没有则为空 |

返回结果同时带 `run_id`、`attempt`、`requirements_rev` 和 `template_ref`，由主会话识别重复或过时结果。

## 升级依据

由 T001 实测提炼：派发稿提供具体接口合同；监督者独立核验并反馈最小复现；中断恢复先检查已有执行，防止重复派发。1.0.0 文件保持不变，在途执行包继续固定原引用。此次升级未改变输入/输出字段合同。
