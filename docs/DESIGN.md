# GitHub 首版设计

日期：2026-11-17。本文保留早期设计原稿；其中状态语句描述当时的探索阶段。当前实现、采用的合同与实际验证以 CONTEXT_CARD.md、RUNTIME_CONTRACT.md 和完成审计为准。

## 1. 已确定的方向

- 用标准化模板安排事情，模板可以迭代升级。
- 一个主会话接收信息、监督 Issue，并安排 Worker。
- 首版仓库为 `ag-jin/auto-ai`；先用 GitHub 承载任务与交付记录。
- 规则命中只进入候选池。主会话先整理任务稿，用户明确选择开发、暂缓或忽略；只有已确认版本可派发。
- 前端覆盖规则、候选需求、任务稿审阅、执行与阻塞、PR 验收及明确合并。最终验收由用户和设计监督负责。

主会话是一个持续的逻辑角色，可在进程或会话重启后恢复；持久状态不能只留在聊天历史中。已采用 Pi 的 `deepseek-flash / high` 进行 Worker 实测；主会话宿主与常驻运行位置仍待选定。

## 2. 职责与最小运行结构

| Module | Interface 与职责 |
| --- | --- |
| 主会话 | 接收目标与变更，读取任务和模板，安排 Worker，处理例外，核验并汇总结果 |
| 执行循环 | 维护事件消费、任务占用、资源上限、超时、重试和结果回写；确定性事项由程序处理 |
| Worker | 接收一份完整执行包，按模板工作，返回产物、证据或具体阻塞 |

首版建议：一个本地运行进程，按需启动 Worker；GitHub 保存持久任务与结果，本地小型状态库保存执行占用、事件游标与进程信息。模板放 Git 仓库中，不引入可视化流程编辑器。

这属于候选实现结构。GitHub 用于托管代码和任务，不代表 Worker 已部署在 GitHub 上。常驻运行位置与离线行为需要在运行时实现前明确。

## 3. 两种模板，各有一个职责

**Issue 表单**只收集“这次要做什么”：目标、验收要求、范围与参考。

**执行模板**规定“这类事情怎么处理”：输入、执行方法、交付物、核验方式和例外处理。

首版模板为带少量 YAML 元数据的 Markdown 文件。主会话按自然语言方法安排执行；暂不建设通用 DAG 或流程解释语言。`templates/catalog.yml` 是当前默认版本的唯一入口。

模板自己的 `schema_version` 表示格式版本，`version` 表示方法版本。示例：

```text
templates/catalog.yml
templates/development/1.0.0.md
templates/research/1.0.0.md
```

## 4. 一件事情如何推进

1. 按仓库、标签、作者、关键词和状态收集 Issue，持久记录命中/排除原因并去重。
2. 主会话为候选选择模板、整理目标/范围/验收/待决策项，形成有版本的任务稿。
3. 用户审阅后选择开发、暂缓或忽略。确认只针对当前任务稿版本；待决策项未处理或需求变更后，需要重新确认。
4. 执行循环核对持久化的开发授权，原子占用任务、生成固定模板的执行包，再启动 Worker。
5. Worker 返回结果、检查输出或阻塞；主会话核验、安排范围内修复或给出具体等待条件，准备关联 PR。
6. 用户和设计监督验收后，用户明确发起合并。执行者不会因测试通过或标签命中而自行合并。

已知任务的后续事件按 Issue 标识送回对应工作；新的目标或跨任务关系由主会话判断。

主会话统一对外更新。Worker 的全量日志与中间推理不逐条写入 Issue。

## 5. 每次派发都固定执行包

```yaml
issue_ref: ag-jin/auto-ai#123
run_id: run-example-001
attempt: 1
template_ref: <full-git-commit>:templates/development/1.0.0.md
requirements_rev: <hash-of-effective-requirements>
inputs:
  goal: 修复订单重复提交
  acceptance:
    - 快速连点只产生一笔订单
  scope: <确认后的项目与允许范围>
  context: <相关文件和讨论引用>
limits: <本次允许的时长、修复次数和资源上限>
```

以上是合同样例，编号与引用均为占位符，不代表已派发任务。

T001 已实现其中的最小执行包生成模块，并增加 `schema_version` 与 `template_text`；目前显式传入模板路径，尚不处理 `limits`、catalog 选择、监听或调度。实际接口以 [T001 任务稿](worker-trials/T001-task.md) 为准。

Worker 不能依赖主会话的隐含聊天上下文。主会话交付的是完整目标与所需引用，Worker 按需读取更多项目细节。

用户改变要求时更新 `requirements_rev`。旧版本结果可保留为证据，但不得直接用于当前任务结项。

## 6. 模板如何升级

1. 从真实任务的失败、反复澄清或交付缺口中提炼改进点。
2. 修改草稿，使用代表性任务检查方法是否可执行、输入是否足够、验收是否清楚。
3. 新增版本文件并记录改进原因，更新 catalog 的默认指针；已发布版本按约定保持不变。
4. 新任务固定新引用，在途任务保留旧引用。需要迁移时，由主会话记录原因、差异和重新核验要求。

即使路径相同，Git commit 也必须固定，避免任务执行时读到变化后的内容。模板不能通过升级自行扩大任务授权。主会话可提出模板改进，发布遵守仓库约定的审查权限。

## 7. GitHub 上最少的可见状态

| 标签 | 含义 |
| --- | --- |
| `auto:inbox` | 新任务或等待安排 |
| `auto:running` | 已有执行尝试在推进 |
| `auto:waiting` | 等待输入、依赖、主动恢复或外部条件 |
| `auto:review` | 有交付物，正在核验或等待验收 |
| `auto:done` | 已达到当前验收要求 |

标签是状态展示，不用于实现互斥锁。每个任务保持一个机器维护的状态摘要，记录模板引用、当前执行、进展、产物和 `next_action`；需要等待时说明具体唤醒条件。

GitHub 是原始 Issue 与 PR 状态的事实来源；本地持久化记录拥有任务稿版本、用户决定、执行尝试和事件。Issue 状态摘要与前端是这些记录的展示，不另建需要人工同步的权威副本。用户要求手动关闭、取消或重开 Issue 时，主会话应重新核对任务意图；“已关闭”本身不能证明验收通过。

当前表单为新 Issue 添加 inbox 标签；在运行时实现前，这只用于整理任务，不会派发执行。

## 8. 监督与恢复的最低要求

- 首版只有一个调度者，使用本机单实例锁与事务占用；同一项目默认一个写入者。标签、评论和聊天记忆均不充当锁。
- 为事件与尝试保留稳定标识，重复通知不重复派发；主会话自己的状态更新不生成新任务。
- 首版监听可采用本地进程定期读取 Issue 的方式，后续再按需要接 webhook。轮询不应在没有新事件时调用模型。
- 重启时先恢复执行记录并核对进程身份；归属或外部结果不明时保留现场，不能直接再执行一次。
- 检查失败进入修复；临时接口故障按有上限的策略重试；相同失败反复出现或预算耗尽后给出明确阻塞。
- 判断进展应看产物和检查结果，不能只看进程是否存活或是否有日志输出。
- 接受用户暂停后先阻止新派发，再停止当前 Worker；停止未确认前保留占用与停止中状态。
- GitHub 回写失败时保留已完成尝试，恢复后补写结果，避免因远端暂时不可写而重新执行。

运行时只处理配置仓库与可信操作者的有效请求。普通引用、第三方内容和 Worker 输出不自动扩大授权。具体的身份检查与凭据使用在接入时实现。

## 9. 首版验收

在隔离项目中，用一个真实 Issue 完成“选模板 → Worker 执行 → 项目检查 → 主会话核验 → 回写结果”。另外验证重复事件、运行中补充、重启恢复、等待输入和模板升级。

特别核对：默认模板从 v1 升到 v2 后，正在执行的 v1 任务仍可按固定引用继续；新任务使用 v2。模拟执行器只能证明调度逻辑，真实 CLI 闭环需单独运行。
