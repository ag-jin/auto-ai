# Execution Route

## 当前状态

已确定 GitHub、主会话、Worker 与版本化模板的基本分工。Pi 的 `deepseek-flash / high` 已用于 T001 开发与返修；执行包生成模块已有代码和验证，自动调度尚未实现。

## 执行路线

| 项目 | 约定 |
| --- | --- |
| 目标 | 最小化实现 Issue → 选择模板 → Worker → 核验 → Issue 结果回写 |
| 本轮技能 | `writing-for-agents` 收敛任务稿；`codebase-design` 收敛职责；`web-access` 核对官方资料 |
| 事实来源 | 用户决定、当前仓库文件、实际执行日志与 GitHub 读回结果 |
| 现有规格 | `docs/DESIGN.md` |
| 模板来源 | `templates/catalog.yml` 指向的版本，并固定 Git commit |
| next_action | 按 Worker 任务稿格式，安排 Pi 执行器 Adapter：从执行包启动 Pi、收集结束结果并验证取消 |

任务板、锁和调度状态后续若进入托管技能体系，应先核对当时可用的 `task-board` 所有权，保持单一事实来源。本轮没有部署运行时或修改托管技能系统。

## 实施顺序

1. **封装真实执行接口**：已确认 Pi 的模型、high 配置与单次执行；接下来验证输出读取、退出判断、取消、进程身份和恢复方式。
2. **实现单任务闭环**：从配置仓库读取任务，选择固定模板，启动 Worker，收集证据并回写结果。
3. **补齐监督和恢复**：验证去重、占用、暂停、重试、要求变化和应用重启。
4. **验证模板升级**：新任务使用新版，在途任务保留旧版；确认失败不会重复交付。

GitHub Issue 和运行日志应保留可恢复记录，长任务从项目文件与实际状态继续。

## 第一项验收样例

在隔离测试仓库提交一项小修复，明确预期行为和测试方式。提交后由系统自行选择开发模板，执行检查并给出结果；全过程无需人工拆卡或反复催进度。

首版尚需验证的能力不能由静态 YAML 检查替代。
